# MyUniClean parity delivery plan

This original five-workstream plan treats MyUniClean as a workflow reference and Epic Laundry as the product being built. The active sequence is now [the 16-phase execution roadmap](myuniclean-16-phase-execution-roadmap.md); the sections below remain implementation evidence and historical grouping, not a five-phase completion claim. Epic Laundry keeps its own brand palette and uses its existing 2D icon system where an icon improves recognition.

## Phase 1 — audit baseline and interaction inventory

**Goal:** build a reliable reference before introducing further UI changes.

- Audit every primary route, visible submenu, dropdown, list mode, modal, empty state and filter in MyUniClean without submitting a write action.
- Record a control-level inventory: source behavior, Epic route/component, parity status, and required improvement.
- Keep MyUniClean's useful patterns: blue utility-shell hierarchy, compact operational cards, filter clarity, report presets and quick actions.
- Restore and lock Epic Laundry's existing purple, evergreen and gold visual system.
- Use existing Lucide 2D icons consistently with a visible label or a durable tooltip/ARIA label.

**Completion evidence:** audit ledger, screenshot references, exact route map, a gap list ordered by daily operational impact.

## Phase 2 — shell, dashboard and discovery

**Goal:** make daily work obvious in one screen.

- Align shell navigation, global search, responsive menu behavior, header utilities and settings entry point with the audited flow.
- Reconcile every dashboard KPI, pipeline tile, attention card and quick action to a readable Epic filter route.
- Distinguish display-only totals from navigation controls.
- Add only small, recognisable icons where they reduce scanning effort.

**Completion evidence:** desktop and narrow-screen manual walkthrough, all dashboard drilldowns verified, keyboard labels verified.

**Current completion evidence (28 September 2026):** Epic’s desktop and compact navigation has been walked through in the isolated demo. The compact menu opens from its labelled trigger, exposes the same grouped destinations, traps keyboard focus, and closes with Escape. Dashboard drill-down routes use readable queue/filter state. Store Orders now includes a source-backed `More filters` panel, active-filter count and Clear action; the demo check confirmed a source filter narrowed results and Clear restored the full result set. No order state was changed during this check.

## Phase 3 — order and customer workflow

**Goal:** reproduce the counter workflow without losing safe commits.

- Compare customer search/add, delivery choices, service/category filters, garment quantities, colour/type, price override, charges, discounts, tax, payment and remarks control-by-control.
- Close any remaining small-function gaps in the shared booking builder.
- Keep order amendments in the builder and separate history/summary from status-changing actions.

**Completion evidence:** reversible draft test, create-order test with controlled demo data, edit-order test, order history/summary test.

**Current implementation evidence:** the booking builder has been compared to the observed customer-to-commit sequence. It supports store customer lookup and, since 1 October, a separate permission-gated customer-profile Save/Cancel path that returns to the still-unbooked order draft; only a saved customer can now satisfy the booking boundary. Existing-customer selection, no-match feedback, duplicate/invalid handling and draft preservation pass focused UI tests with intercepted customer responses; the separate customer API self-test passes in a temporary database. Production web mode currently supports name and phone only, and admin-configurable customer fields remain open. Other available controls include pickup/home/express fulfilment, expected delivery date, service/category filtering, garment search, quantity, colour, care type, price override, configured pricing rules, payment choice, notes, photo capture, held drafts and an explicit final booking action. The prior controlled local-demo create passed: the receipt appeared after explicit commit, the order entered Store Orders, and the associated customer work card opened read-only. A controlled amendment also passed, creating a replacement invoice while retaining the order history. Retired tags are no longer included in the active traceability count; garment attribute validation, quick-add and full booking verification remain open.

- Verify grouped settings editors and their explicit save boundaries.
